# Responsive Web Visualization 3

## Context: Who

The third web visualization addresses the actor-level question of the project:

> **Which armed actors display different profiles of violence?**

After identifying **when** violence changes and **where** different forms of violence concentrate, this representation shifts the unit of analysis from time and space to the **armed actors themselves**. The objective is to compare actors across several dimensions simultaneously rather than reducing their behavior to a single measure such as total events or fatalities.

The underlying idea is that two actors can participate in similar amounts of conflict while having substantially different profiles. One may be primarily involved in direct combat, another may have a comparatively larger share of one-sided violence, while another may operate over a much wider geographic area. The visualization therefore combines combat activity, losses suffered, one-sided violence, civilian fatalities, relative violence composition, and geographic spread. 

A conventional table could list these indicators, but comparing many actors across six variables would require repeatedly scanning rows and columns. A **parallel-coordinates plot** instead represents each actor as a single visual trajectory, allowing multidimensional profiles to be compared as shapes.

The representation is therefore intended to answer questions such as:

* Which actors are highly active in direct combat?
* Which actors are associated with more one-sided violence?
* Which actors have particularly high civilian fatalities associated with one-sided violence?
* Do actors with similar levels of activity differ in their one-sided violence share?
* Which actors operate across the widest geographic area?
* Are there actors whose overall profile differs substantially from the rest?

## Representation: Parallel Coordinates ("03 / WHO?")

### What it represents

How individual armed actors differ in their violence profile: combat involvement, losses suffered, one-sided violence against civilians, and geographic reach.

### What it shows

The main representation is a **parallel-coordinates plot**, where each polyline corresponds to one armed actor and crosses six fixed quantitative axes:

1. **Combat events** — `combat_event_count`
2. **Actor deaths** — `actor_deaths_suffered`
3. **One-sided events** — `one_sided_event_count`
4. **Civilian fatalities** — `one_sided_civilian_fatalities`
5. **One-sided share** — `one_sided_event_share`
6. **Geographic spread** — `active_h3_cell_count`

A detail panel on the right displays additional information about whichever actor is currently hovered or selected. 

![Web 3](https://github.com/PayThePizzo/war-civilian-violence/blob/main/docs/phase_3/images/Web3.png?raw=TRUE)

Visually, the representation consists of a series of **vertical parallel axes**, each corresponding to a different property of an armed actor. Every actor is represented by a polyline connecting its position on each axis. A higher position indicates a larger value for that particular dimension.

The shape of the line is therefore more important than any single point. An actor whose line remains high across most axes represents a very different violence profile from one that is high only for combat activity or only for one-sided violence.

Because event and fatality variables are highly skewed, their axes use a **symlog scale** rather than an ordinary linear scale. The one-sided share instead uses a fixed linear scale between 0% and 100%. This scaling prevents a small number of very large actors or fatality values from compressing most of the remaining observations near the bottom of the plot. 

The screenshot illustrates the profile of **SFA**. Its highlighted line crosses relatively high positions on several dimensions. The detail panel reports 567 total events, including 424 combat events and 143 one-sided events. One-sided events therefore represent 25.2% of its recorded events. The selected profile also shows 61,973 one-sided civilian fatalities, 2,993 actor deaths suffered, and activity across 114 H3 cells.

These numbers are not intended to be read as a single performance score. Instead, they describe different dimensions of the actor's recorded conflict activity. In particular, `actor_deaths_suffered` is kept distinct from fatalities recorded in events involving the actor, specifically so that losses suffered by the actor are not confused with broader event fatalities. 

The right-hand **detail panel** complements the parallel coordinates by recovering exact values that would otherwise be difficult to read precisely from line position alone. It groups the selected actor's information into four sections:

* **Activity** — total events, combat events and active weeks;
* **One-sided violence** — one-sided events, one-sided share and one-sided civilian fatalities;
* **Losses / geography** — actor deaths suffered and geographic spread;
* **Active period** — first and last recorded event.

This combination gives the visualization two levels of reading: the parallel coordinates provide **comparative pattern recognition**, while the details panel provides **exact values for one actor**. 

### Interaction

The visualization includes several interactive mechanisms.

* **Hover:** hovering an actor's line highlights it, fades the other actors and updates both the small cursor tooltip and the detailed panel.
* **Click:** clicking a line selects that actor globally. This selection is shared with the other web visualizations: the Timeline changes to that actor's weekly series, the Map restricts its spatial data to that actor, and the Before/After visualization changes to that actor's episodes.
* **Show minor actors:** by default, only actors satisfying the preprocessing eligibility threshold are displayed. The checkbox reveals all actors when a more complete comparison is required.
* **Persistent selection:** the globally selected actor remains visually distinct even while another actor is temporarily hovered.
* **Larger invisible hit areas:** each visible line has a wider invisible interaction path, making thin polylines easier to select with the pointer. 

The **Show minor actors** option is important because all actors remain in the analytical dataset; the preprocessing pipeline does not remove actors with relatively few events. Instead, it creates the `eligible_for_web3` flag according to a minimum-event threshold so that the initial visualization remains readable while still allowing the complete dataset to be explored.

## Knowledge: What can we learn from it?

The main purpose of this representation is to determine whether armed actors that participate in the same conflict exhibit **different multidimensional violence profiles**.

The important question is not simply which actor recorded the largest number of events. Instead, we want to understand how several properties combine.

For example, two actors could have similar numbers of combat events but differ substantially in:

* the number of one-sided events attributed to them;
* the share of their activity represented by one-sided violence;
* the number of civilians killed in those events;
* the losses suffered by the actor itself;
* the geographic extent of its activity.

The actor-profile dataset was specifically constructed for this comparison and contains exactly one row per canonical actor, together with temporal, behavioral, fatality and geographic measures. 

In a tabular representation, these values could certainly be sorted or inspected individually. What is difficult to see, however, is the **relationship among all dimensions at the same time**.

A table does not immediately reveal:

* actors whose violence profiles have similar overall shapes;
* actors that are high on almost every activity dimension;
* actors with high combat involvement but relatively little one-sided violence;
* actors with modest event counts but a relatively high one-sided share;
* cases where one-sided-event frequency and civilian fatalities diverge;
* actors whose geographic reach is disproportionately large or small relative to their activity;
* multidimensional outliers.

Parallel coordinates convert each row of actor metrics into a recognizable **profile shape**. The viewer can therefore identify patterns through line trajectories rather than repeatedly comparing six numerical columns.

The `one_sided_event_share` axis is especially important because absolute counts alone can be misleading. An actor may have many one-sided events simply because it is involved in a very large number of events overall. The share measure instead describes the relative composition of that actor's activity:

$$
\text{one-sided event share}
=
\frac{\text{one-sided events}}
{\text{total events}}
$$

This makes it possible to distinguish **high absolute involvement** from a **high relative orientation toward one-sided violence**.

Likewise, geographic spread introduces information that cannot be obtained from event counts alone. Two actors with similar numbers of events may differ because one operates within a relatively concentrated area while another is active across many H3 cells. The actor dataset measures this using the same H3 spatial resolution used by the map, keeping the spatial interpretation consistent across Web 2 and Web 3. 

The representation therefore provides the actor-level component of the project's narrative. The Timeline answers **when** the conflict changes, the Map shows **where** those patterns occur, and the parallel-coordinates view identifies **which actors have different violence profiles**.

Selecting one of those actors then provides the bridge to the final visualization, which examines **what happens before and after that actor's major episodes of one-sided violence against civilians**.

## Pipeline from raw information to the visualizations

The actor view reads one derived file, `actor_profiles.csv`. All analytical work happens upstream in the Python pipeline, while the browser only filters, scales and lays out.

The whole pipeline runs with `python scripts/build_all.py`.

**What is inside the raw dataset.**

- Each UCDP GED event names its two sides (`side_a`, `side_b` with ids) and the violence type. A combat event involves two armed actors; a one-sided event has one perpetrator (`side_a`), and civilians are never treated as an actor.

**What is inside `actor_profiles.csv`.**

- One row per canonical actor (22 actors, 11 flagged `eligible_for_web3`). 

The parallel-coordinates plot uses six fixed axes:

| Column | Axis |
|---|---|
| `combat_event_count` | combat involvement (symlog scale) |
| `actor_deaths_suffered` | losses suffered (symlog scale) |
| `one_sided_event_count` | one-sided events (symlog scale) |
| `one_sided_civilian_fatalities` | civilian toll (symlog scale) |
| `one_sided_event_share` | share of the actor's events that were one-sided (linear, 0 to 1) |
| `active_h3_cell_count` | geographic spread (symlog scale) |

The detail panel also shows:

- `total_event_count`, first/last event date, active weeks and per-active-week rates;
- `combatant_fatalities_in_involved_events` counts deaths in combat events the actor took part in and is not the actor's own losses;
- `actor_deaths_suffered` is kept separately for that.

### Steps

1. **Download the raw GED** (v26.1) into `data/raw/GEDEvent_v26_1.csv`, kept unmodified.
2. **`01_clean_events.py`** validates required columns, unique event ids, parseable dates and `date_start <= date_end`, restricts the data to Sudan and 2023-04-15 to 2025-12-31, derives `combatant_fatalities`, `civilian_fatalities` and `one_sided_civilian_fatalities`, and flags (does not drop) events with invalid coordinates. Output: `data/processed/events_clean.parquet`, one row per event.
3. **`02_build_actor_events.py`** expands each event into actor × event rows (a combat event becomes two rows, one per side; a one-sided event becomes one row, the perpetrator). Output: `data/processed/actor_events.parquet` and `actor_lookup.csv`.
4. **`05_build_actor_profiles.py`** groups the actor-event rows by `actor_id`, attaches the canonical name from `actor_lookup.csv`, and computes activity, fatality, one-sided and geographic-spread metrics (spread uses H3 cells at the same resolution as the map, from spatially eligible events only). It sets `eligible_for_web3` from `actors.min_events` (5) but removes no one. Output: `data/derived/actor_profiles.csv`.
5. **`07_validate_outputs.py`** runs 146 checks (all pass) over every processed and derived file. `build_all.py` runs all stages in order, stops at the first failure, and also writes `metadata.json` (country, analysis period, week convention, H3 resolution, window size).
6. **`npm run sync-data`** (in `web/`, run automatically by `npm run dev` and `npm run build`) copies the five derived files unchanged into `web/.generated/data/`.
7. **At startup** `src/data/loaders.ts` fetches and parses the files through `parsers.ts`, which fails loudly on schema drift and keeps `null` (not observed) distinct from `0`. Views read only through `src/data/selectors.ts`.
8. **`ActorParallelCoordinates.ts`** takes `getActorProfiles(data, showMinorActors)`, which keeps only `eligible_for_web3` rows unless the 'Show minor actors' box is ticked (the threshold is never re-derived in the browser). `actorMath.ts` builds one scale per axis (symlog for the skewed counts, linear for the share) and the polyline points; each actor is one line.
9. **Interaction:** hovering highlights an actor's line and fills the detail panel (local state); clicking a line writes `selectedActorId` to the global store, which switches the timeline to that actor's series, restricts the map to its cells and shows its episodes in the before/after view.
